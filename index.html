L-01 · Mobile

BagHop Driver

I took over an unreleased driver app for a luggage-delivery service and shipped it to both app stores. It wraps the client's Bubble web app in React Native and adds what a web app cannot do: background GPS, push alerts for nearby pickups, luggage photos and the permission flows they need.

  • Platform upgrade. Google Play now requires 16 KB memory pages. I tested published builds to find the lowest React Native version that met it, then upgraded 0.73 → 0.77 across Gradle, AGP, Kotlin, NDK and AppDelegate. The final bundle had zero misaligned native libraries, targeting SDK 36.
  • Location and push. Continuous background location (a Kotlin foreground service on Android, background updates on iOS), push to every device a driver uses with dead tokens pruned, and a high-importance channel so pickup alerts show as banners.
  • Remote debugging. Found production bugs from nginx logs and Firestore alone, such as a status poller tracking the wrong driver after re-login, and a login handler where a failed push token silently stopped GPS.

S-02 · AI & LLM · Civil engineering

ICT construction plan system ICT施工計画書システム

A civil contractor has to file an ICT construction plan for each job. In this system an LLM drafts the plan from the uploaded design documents using RAG. Engineers correct the draft and export it to Excel in the client's own template, or to PDF or Word.

  • Design from real data. Before building, I analyzed 26 completed jobs (529 files). Only about 2% of the drawings were machine-readable DXF, so I separated drawing analysis from storage: SFC and P21 files are kept and clearly labelled instead of rejected.
  • Review workflow. Separate roles for contractor and engineering staff: intake, AI draft, clarification Q&A, field-by-field corrections with reasons, then approval or rejection. Every step is written to an audit log.
  • Training data. Each correction is stored as model output, human fix and reason. A review gate lets only approved corrections become training data.
  • Delivery. Keyless CI/CD to Cloud Run through Workload Identity Federation, the full loop verified in production, and 12 design documents (requirements, architecture, ER, API, deployment, disaster recovery).

S-03 · Real estate · Geometry

Land-acquisition toolkit 建売仕入支援ツール

A builder of ready-made houses decides whether to buy a plot by working out how many lots it splits into, what house fits on each, and whether the numbers still make a profit at the asking price. Staff did this by hand in CAD and Excel. I built three connected tools that do it, and each passes its result to the next, so a plot is entered only once.

  • Lot division (区割). Generates frontage and flag-lot (旗竿地) plans and checks minimum lot area, the 2 m road-frontage rule and the setback for narrow Article 42-2 roads. Every plan's score is shown line by line, so a planner can see why one plan won.
  • Building volume (間取り). Reads the site from an uploaded drawing, then places parking, the building and a 1F / 2F room zoning inside coverage, floor-area and setback limits.
  • Purchase decision (仕入会議資料). Solves for the highest land price that still clears the target margin, by bisection over the full cost model: brokerage, demolition, utilities, construction, sales costs and interest. The ten-page A4 meeting document adds maps, photos, the survey and comparable sales.
  • Scope and quality. Sorted every request into MVP, phase 2 or not to build, to fit a fixed budget. Scraping REINS and SUUMO is against their terms, so the tool reads the PDFs staff already download. The DXF, Excel and PDF exports are each checked with a different tool from the one that wrote them, and lazy loading cut the first download from 1.9 MB to 524 KB.

S-04 · Survey · Desktop

Land-CAD GNSS integration

I connected a survey-grade GNSS receiver to a desktop app that shows a DXF drawing and captures points on site. Points are converted from WGS84 into the site's local coordinates with a 7-parameter Helmert fit (Umeyama / SVD), checked with residuals, leave-one-out validation and point-spread checks.

  • Architecture. A cloud service cannot reach a Bluetooth device on a laptop, so I moved the GNSS connection layer from the Cloud Run backend into Electron's main process (about 1,300 lines of TypeScript) and checked the port byte for byte against the original parser.
  • Hardware protocol. Implemented the hardware team's STM32 control protocol through three revisions (v1.1 → v1.3) while the hardware itself was still being brought up.
  • RTK FIX. The app stopped at Differential while other software reached RTK FIX. The NTRIP client never sent GGA positions to the VRS caster. I fixed it and replaced a connected / disconnected flag with a four-state connection model for diagnosis.

S-05 · CAD · Desktop

DXF Platform: 2D civil drawings to 3D LandXML

A pipeline that takes a 2D Japanese civil-engineering DXF drawing, extracts survey control points and road geometry, builds a Delaunay TIN with IDW-interpolated elevation and writes a LandXML 1.2 surface. A C# WPF desktop client handles upload and preview.

  • Hidden elevations. In these drawings no entity has a non-zero Z. Elevations are plain-text labels on a separate layer next to the survey points, which is in no public spec. I wrote extraction that matches each label to its nearest point, and the Z values matched the client's reference data.
  • Silent CAD failure. BricsCAD and TREND-POINT refused to open the output with no error. The cause was Linux line endings. Normalizing to CRLF fixed it.
  • Without the target software. Both CAD tools are Windows-only and I had no copies. I diagnosed both problems from the client's sample DXF and reference XML files and verified the fixes by parsing the output.
